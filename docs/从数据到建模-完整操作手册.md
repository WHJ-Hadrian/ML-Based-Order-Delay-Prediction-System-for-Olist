# Olist 订单配送延误分析系统 · 从数据到建模完整操作手册

> 适用对象：第一次上手本系统、需要完成一次“数据分析 → 模型训练 → 预测评估 → 报告导出”的同学。
>
> 目标场景：基于 Olist 巴西电商平台订单数据，预测订单是否延误（`is_delayed`）。
>
> 阅读建议：先照着“路线 A”在 30 分钟内跑通全流程，再用“路线 B”从原始 8 张表完整复现数据处理过程。

## 第三步：数据处理（路线 B 才需要）

路线 A 的数据已经加工好，可以跳过这一步，直接进入第四步。

### 3.1 新建数据处理任务

1. 打开左侧“数据处理”。
2. 点“新建数据处理”。
3. 在弹窗中选择：

   ```text
   数据集库：Olist 原始数据
   数据集版本：v1
   ```

4. 点“创建并配置”。
5. 页面会展开当前任务的编辑器，顶部可以看到“处理节点”“保存”“校验流程”“预览运行”“运行处理并生成版本”“发布版本”。

### 3.2 认识可用的节点

点“添加处理节点”，可选类型有：

| 节点 | 用途 |
|---|---|
| 数据检查 | 校验字段值，可只记录、告警、阻断发布、移除记录或隔离记录 |
| 字段转换 | 去空格、转大小写、填充缺失值、替换文本、转换类型 |
| 行筛选 | 按条件保留记录 |
| 字段选择 | 只保留需要的字段，去掉多余字段 |
| 去重 | 按一个或多个字段去重 |
| 数据关联 | 用字段键连接两张表或上游节点结果，支持 LEFT/INNER 等 |
| 分组聚合 | 按字段分组，生成计数、求和、平均、最小值、最大值、去重计数 |
| 派生字段 | 用结构化表达式生成新字段 |
| 输出 | 把上游结果物化为新的数据版本 |

节点按从上到下的顺序执行。每个节点都要选择“输入”，可以是某张数据表，也可以是上游节点的输出别名。

### 3.3 先处理订单商品明细（避免行数膨胀）

目标：把一个订单的多行商品聚合成一行。

1. 添加“数据关联”节点：
   - 左侧数据：`olist_order_items_dataset`
   - 右侧数据：`olist_products_dataset`
   - 关联键：左 `product_id` = 右 `product_id`
   - 关联方式：`保留全部左侧记录（LEFT）`
   - 数据基数：`多对一（N:1）`
   - 输出别名：`items_with_product`
2. 添加“分组聚合”节点：
   - 输入：`items_with_product`
   - 分组字段：`order_id`
   - 指标：
     - `item_count` = `COUNT(*)`
     - `total_price` = `SUM(price)`
     - `total_freight` = `SUM(freight_value)`
     - `seller_count` = `COUNT_DISTINCT(seller_id)`
     - `product_category` = `MAX(product_category_name)`
   - 输出别名：`order_items_agg`

> 界面里对应关系：`COUNT(*)` 选“计数 / 记录数（无需字段）”，`SUM` 选“求和”，`COUNT_DISTINCT` 选“去重计数”，`MAX` 选“最大值”。

3. 添加“数据关联”节点：
   - 左侧数据：`olist_orders_dataset`
   - 右侧数据：`olist_customers_dataset`
   - 关联键：左 `customer_id` = 右 `customer_id`
   - 关联方式：`保留全部左侧记录（LEFT）`
   - 数据基数：`多对一（N:1）`
   - 勾选“右侧键必须唯一”，最大展开倍数设为 `1`
   - 输出别名：`orders_customers`
4. 添加“数据关联”节点：
   - 左侧数据：`orders_customers`
   - 右侧数据：`order_items_agg`
   - 关联键：左 `order_id` = 右 `order_id`
   - 关联方式：`保留全部左侧记录（LEFT）`
   - 数据基数：`一对一（1:1）`
   - 勾选“右侧键必须唯一”，最大展开倍数设为 `1`
   - 输出别名：`orders_base`

**为什么先聚合**

订单商品表一个订单有多行。如果直接 `orders LEFT JOIN order_items`，订单行会被复制，后续延误率会被重复计数。先把商品聚合成“一订单一行”，再做 1:1 关联，才能保证标签和统计正确。

### 3.4 清洗

1. 添加“数据检查”节点：
   - 输入：`orders_base`
   - 条件：`order_delivered_customer_date` `为空`
   - 命中效果：`移除记录`
   - 输出别名：`delivered_only`

   这一步去掉未签收订单，避免把“还没送到”误判成“未延误”。

2. 再添加“行筛选”节点：
   - 输入：`delivered_only`
   - 条件：`order_status` `等于` `delivered`
   - 输出别名：`delivered_orders`

3. 可选：添加“去重”节点，去重键选 `order_id`。如果前面的 1:1 关联配置正确，这一步应该没有重复行；保留它是为了兜底。

### 3.5 派生延误标签与特征

依次添加“派生字段”节点。每个节点都填写“新字段”“数据类型”“输出别名”“表达式”。

#### 3.5.1 延误标签 `is_delayed`

- 新字段：`is_delayed`
- 数据类型：`整数`
- 表达式类型：`条件分支`
- 条件：`日期相差天数(客户签收时间, 预计送达日期)` `大于` `常量 0`
- 满足条件时：`常量 1`
- 否则：`常量 0`

含义：客户实际签收日期晚于预计送达日期，就是延误。

#### 3.5.2 延误天数 `delay_days`

- 新字段：`delay_days`
- 数据类型：`整数`
- 表达式类型：`条件分支`
- 条件：`日期相差天数(客户签收时间, 预计送达日期)` `大于` `常量 0`
- 满足条件时：上面的日期相差天数
- 否则：`常量 0`

#### 3.5.3 实际配送天数 `total_delivery_days`

- 新字段：`total_delivery_days`
- 数据类型：`整数`
- 表达式类型：`日期相差天数`
- 被减日期（左）：`order_delivered_customer_date`
- 减去日期（右）：`order_purchase_timestamp`

#### 3.5.4 下单月份 `purchase_month`

- 新字段：`purchase_month`
- 数据类型：`整数`
- 表达式类型：`提取日期部分`
- 日期部分：`月份`
- 字段：`order_purchase_timestamp`

#### 3.5.5 下单星期 `purchase_weekday`

- 新字段：`purchase_weekday`
- 数据类型：`整数`
- 表达式类型：`提取日期部分`
- 日期部分：`星期`
- 字段：`order_purchase_timestamp`

#### 3.5.6 下单小时 `purchase_hour`

- 新字段：`purchase_hour`
- 数据类型：`整数`
- 表达式类型：`提取日期部分`
- 日期部分：`小时`
- 字段：`order_purchase_timestamp`

#### 3.5.7 运费占比 `freight_ratio`

- 新字段：`freight_ratio`
- 数据类型：`小数`
- 表达式类型：`数值运算`
- 运算符：`除`
- 左参数：`total_freight`
- 右参数：`total_price`

系统对除数为 0 的情况返回空值，不会让任务失败。

#### 3.5.8 预计配送天数 `estimated_delivery_days`（可选）

- 新字段：`estimated_delivery_days`
- 数据类型：`整数`
- 表达式类型：`日期相差天数`
- 被减日期（左）：`order_estimated_delivery_date`
- 减去日期（右）：`order_purchase_timestamp`

注意：这个字段只适合“订单已审批、尚未送达”的预测时点。如果你的论文定义是“下单瞬间预测”，不要把它放进特征。

#### 3.5.9 配送距离 `distance_km`（进阶，可选）

配送距离需要把客户邮编和卖家邮编分别关联到经纬度表，再用“经纬度距离”表达式计算。步骤较繁琐：

1. 对 `olist_geolocation_dataset` 按邮编前缀分组，求平均纬度和平均经度。
2. 分别关联客户表和卖家表，得到客户经纬度、卖家经纬度。
3. 派生字段选“经纬度距离”，按“起点经度、起点纬度、终点经度、终点纬度”填入。

如果时间有限，建议直接用路线 A 的 `orders_delay_train70.csv`，里面已经包含 `distance_km`。

### 3.6 选择最终字段

添加“字段选择”节点：

- 输入：最后一个派生节点的输出
- 保留字段建议：

```text
order_id
is_delayed
delay_days
total_delivery_days
purchase_month
purchase_weekday
purchase_hour
estimated_delivery_days
item_count
total_price
total_freight
freight_ratio
seller_count
product_category
customer_state
```

`order_status`、各种原始时间戳、`customer_id` 等字段可以在建模时再排除，但提前去掉能让数据版本更干净。

### 3.7 输出新版本

添加“输出”节点：

- 新数据版本名称：`olist_delay_clean_v1`
- 输出方式：`生成数据版本`
- 格式：CSV
- 当前全量执行单次最多 100,000 行

### 3.8 校验、预览、运行、发布

1. 点“保存”。
2. 点“校验流程”。如果节点配置有问题，页面会列出具体节点和原因，按提示修正。
3. 点“预览运行”。在运行抽屉里查看每个节点的输入行数、输出行数、匹配率和最多 100 行样例。
4. 重点检查：
   - 关联后行数有没有异常膨胀。
   - `is_delayed` 是否只有 0/1。
   - `total_delivery_days` 是否有负数。
5. 点“运行处理并生成版本”。等待状态变成“已完成”。
6. 点“发布版本”。

### 3.9 超过 100,000 行怎么办

处理节点和训练都限制单次 100,000 行。推荐做法：

1. 用“行筛选”按时间切分，例如只保留 2017-01-01 到 2018-08-31。
2. 用“分组聚合”先把明细聚合到订单级，行数会显著下降。
3. 拆成多个版本，例如 `olist_delay_2017_v1`、`olist_delay_2018_v1`，分别训练和评估。
4. 直接使用已有的 `olist_delay_train70.csv`（67,529 行）和 `orders_delay_holdout30.csv`（28,941 行）。

## 第四步：发布与字段检查

1. 打开“数据集”，找到刚生成的版本，确认状态为 `READY`。
2. 展开数据集，确认新数据表的行数和字段数。
3. 打开“字段定义”，检查关键字段的逻辑类型：
   - `is_delayed`：类别/整数（0/1）
   - `delay_days`、`total_delivery_days`、`purchase_month`、`purchase_weekday`、`purchase_hour`、`item_count`、`seller_count`：数值/整数
   - `freight_ratio`、`total_price`、`total_freight`：数值/小数
   - `product_category`、`customer_state`：类别/文本
4. 如果字段类型识别错了，在字段定义里改逻辑类型并保存。类型错了会影响分析图和模型特征处理。

## 第五步：统计分析

打开“可视化分析”。这一页做三件事：看单字段分布、看两个字段的关系、把图表加入分析画布并保存方案。

### 5.1 选择数据

1. 左侧“数据集”列选择 `Olist 延误训练集`（或路线 B 生成的清洗版本）。
2. 中间“数据表”列选择对应表。
3. 右侧“字段”列会列出全部字段。

### 5.2 看单字段分布

1. 点击字段名，例如 `is_delayed`。
2. 下方“字段分布图”会显示：
   - 数值字段：直方图。
   - 类别字段：类别频数。
3. 记录关键数字：
   - `is_delayed = 1` 的占比就是整体延误率。
   - `total_delivery_days` 的分布可以看出配送时长集中在多少天。
   - `delay_days` 的分布可以看出延误订单通常晚几天。

### 5.3 看两个字段的关系

1. 先在字段列表点击 X 字段，例如 `purchase_month`。
2. 在“字段关系”面板的“比较字段”下拉框选择 Y 字段，例如 `is_delayed`。
3. 点“分析关系”。
4. 结果规则：
   - 两个数值字段：散点图。
   - 类别字段 + 数值字段：前 12 组的数值均值。
   - 两个类别字段：暂不支持。

**Olist 场景的用法**

| X 字段 | Y 字段 | 能得到什么 |
|---|---|---|
| `purchase_month` | `is_delayed` | 每个月的延误率 |
| `purchase_weekday` | `is_delayed` | 每个星期的延误率 |
| `product_category` | `is_delayed` | 每个商品类目的延误率 |
| `customer_state` | `is_delayed` | 每个州的延误率 |
| `distance_km` | `total_delivery_days` | 距离与配送时长的散点关系 |

> 如果 `purchase_month` / `purchase_weekday` 被识别为数值型，和 `is_delayed` 做关系分析会得到散点图，而不是分组均值。先到“字段定义”把这两个字段的逻辑类型改成类别型，再回到分析页。
> 注意：页面当前展示散点和分组均值，不直接输出皮尔逊相关系数 `r`。如果需要精确的 `r`，把这两列导出后用 Excel 或 Python 计算，再写进报告。

### 5.4 加入画布并保存方案

1. 勾选想批量加入的字段（最多 8 个），点“分析并加入画布”。

## 第六步：训练模型

打开“建模实验”。

页面是三段式：

```text
数据源  →  目标与特征  →  训练分支
```

底部是“运行 N 个分支”。

### 6.1 连接数据源

1. 在“数据源”节点选择数据集，例如 `Olist 延误训练集`。
2. 选择版本，例如 `v1`。
3. 选择数据表。
4. 连接成功后，中间“目标与特征”会列出全部字段。

**检查点**

- 底部显示行数，必须小于等于 100,000。
- 字段数不要过多，建议控制在 20 个以内。

### 6.2 设置目标变量

1. 在字段列表找到 `is_delayed`。
2. 点字段左侧的 `Y` 按钮，把它设为预测目标。
3. 系统会自动判断任务类型为“分类”。
4. 如果目标是连续值（例如 `delay_days`），系统会切换为“回归”。

### 6.3 选择特征（最重要）

勾选字段右侧的“输入”复选框。

**推荐特征（不泄漏）**

```text
distance_km
freight_ratio
total_freight
total_price
item_count
seller_count
purchase_month
purchase_weekday
purchase_hour
customer_state
seller_state
same_state
product_category
total_weight_g
payment_value
payment_installments_max
payment_type_count
product_category_count
estimated_delivery_days（仅在“审批后、送达前”预测时点使用）
```

**绝对不能作为特征的字段**

| 字段 | 原因 |
|---|---|
| `is_delayed` | 目标本身 |
| `delay_days` | 由标签定义直接算出，属于标签泄漏 |
| `total_delivery_days` | 只有送达后才知道，属于未来信息 |
| `order_delivered_customer_date` | 标签定义字段 |
| `order_estimated_delivery_date` | 标签定义字段 |
| `review_score` | 送达后才有，属于未来信息 |
| `order_id` | 纯标识，没有预测价值 |

> 如果把 `delay_days` 或 `total_delivery_days` 选进特征，模型会得到接近 100% 的分数，但上线后完全不可用。这是这类项目最常见的错误。

### 6.4 选择算法

每个训练分支选一个算法。点训练分支右上角的 + 号（添加模型分支），最多可以同时跑 4 个。

推荐组合：

| 任务 | 算法 | 说明 |
|---|---|---|
| 分类 | 随机森林 | 稳定、可解释，适合作为基线 |
| 分类 | XGBoost | 精度高，训练较慢 |
| 分类 | LightGBM | 大数据集速度快 |
| 分类 | 逻辑回归 | 可解释的线性基线 |

SVM 和 KNN 在数据量大时会自动抽样（SVM 约 2 万行，KNN 约 3 万行），算法卡片上有提示。

### 6.5 设置划分与交叉验证

在训练设置里填写：

| 选项 | 推荐值 | 说明 |
|---|---|---|
| 留出集 | 20% | 最终评估用，训练时不能偷看 |
| 验证集 | 0%（或 10%） | 需要调参时再开 |
| 切分策略 | 随机分层 | 类别不平衡时保证训练/测试都有正样本 |
| 交叉验证 | 5 折 | 数据量小用 5 折，数据量大用 3 折 |
| 随机种子 | 42 | 保证可复现 |

如果要做“时间外推”实验，把切分策略改成“按时间顺序”，并选择时间字段。注意：时间字段不能同时作为输入特征，否则会泄漏。

### 6.6 运行训练

1. 确认底部没有红色阻断提示。
2. 点“运行 N 个分支”。
3. 观察进度条和每个分支的状态：排队、运行中、完成、失败、已取消。
4. 某个算法失败时，卡片会显示失败原因，例如数据不足、目标列只有一个值、特征全为空、内存不足。
5. 需要停止时点“取消”。已完成的模型会保留。

训练完成后，每个成功分支会出现一张结果卡。

### 6.7 看结果

每张结果卡包含：

- 算法名称、模型名称、状态标签（`DRAFT` / `APPROVED`）。
- 训练行数、测试行数、创建时间。
- 核心指标：准确率、平衡准确率、加权精确率、加权召回率、加权 F1。
- “解释与详情”加载后显示：
  - 划分摘要。
  - 决策阈值、校准样本数。
  - 分类：ROC-AUC、PR-AUC、宏 F1、宏召回、每类精确率/召回率/F1、TOP 混淆对。
  - 回归：MAE、RMSE、R²、MAPE、解释方差、残差标准差。
  - 交叉验证均值 ± 标准差。
  - ROC 曲线、PR 曲线。
  - 回归的预测值 vs 真实值散点、残差散点、残差分布直方图。
  - 特征重要性（SHAP 全局重要性 + 置换重要性）。

**分类任务优先看什么**

1. `ROC-AUC`：整体排序能力，类别不平衡时比准确率可靠。
2. `宏召回` 和正类召回：延误订单有没有被漏掉。
3. `宏 F1`：正负类综合表现。
4. 混淆矩阵：假阴性（漏报延误）和假阳性（误报延误）的业务代价。
5. 训练集与测试集差距：差距过大提示过拟合。

### 6.8 单样本解释与 What-If

1. 在结果卡点“单样本解释”。
2. 弹窗会用一条背景样本预填特征值。
3. 点“计算解释”，会显示：
   - 预测类别。
   - 正类概率、判定阈值、置信度。
   - 每个特征的 SHAP 贡献条形图（红色推高、蓝色拉低）。
   - 自然语言解释。
   - 反事实建议，例如“将配送距离调整到 591.48 时，预测概率变为 51.3%，结论会翻转”。
4. 修改任意特征值，点“按当前输入重新计算”，会对比原始概率和修改后概率，并显示是否翻转。
5. 点反事实条目可以直接把特征改为建议值。
6. 点“重置输入”恢复原始样本。

### 6.9 导出报告

1. 在结果卡点“导出报告”。
2. 填写报告标题，例如 `Olist 延误预测 · 随机森林评估报告`。
3. 选择格式：PDF、Word、HTML、JSON、CSV。
4. 勾选包含内容：
   - 模型概览
   - 评估指标
   - 模型对比
   - 特征重要性
   - 单样本解释
   - 结论摘要
5. 点“生成并下载”。
6. 下方“导出记录”会记录标题、格式和时间。

PDF 和 Word 适合放进毕业论文；JSON 和 CSV 适合做附录或二次分析。

### 6.10 审批模型

1. 找到表现最好的模型卡。
2. 点“审批”。
3. 状态从 `DRAFT` 变成 `APPROVED`。
4. 只有审批后的模型才表示“可用于推理”。如果不再使用，可以点“弃用”。

> 说明：训练成功时系统已经生成了模型版本，并保存了模型文件、特征配置、预处理参数、评估指标、随机种子和划分比例。“审批”是把状态推进到可用，不是重新训练。

## 第七步：独立评估与预测

打开“评估与预测”。

### 7.1 选择模型

1. “模型版本”下拉框选择 1 个模型；如果要比较，选 2–5 个同任务、同目标的模型。
2. 系统会显示模型名称、任务类型、算法。

### 7.2 选择独立测试数据

1. “独立测试数据”选择 `Olist 延误评估集`。
2. 选择数据集版本 `v1`。
3. 选择数据表。
4. 系统会校验字段是否匹配：
   - 缺少特征会标红“缺少特征”。
   - 与训练数据重叠会标红“与训练数据重叠”。
   - 缺少目标会标黄“缺少目标”。

> 独立评估必须使用训练来源以外的数据集。这是评估泛化能力的关键，不能用训练集自己评自己。

### 7.3 选择评估模式

- `带标签评估`：测试数据里有 `is_delayed`，会计算准确率、AUC、混淆矩阵等。
- `只生成预测`：测试数据没有目标，只输出预测结果和概率。

### 7.4 运行

1. 点“加入清单”。
2. 确认清单里没有红色不兼容项。
3. 点“运行评估”（单模型）或“开始比较”（多模型）。
4. 结果表会显示：
   - 测试数据源
   - 模型版本
   - 各指标
   - ROC-AUC / PR-AUC
   - 宏 F1 / 召回
   - 评估行数 / 预测行数
5. 点某一行，下方会显示预测样例（原始行、实际值、预测值）。
6. “评估记录”会保留历史比较，方便写论文时对比。

### 7.5 怎么解读

- 如果训练集 AUC 0.85、独立测试集 AUC 0.62，说明模型泛化下降明显，可能是概念漂移或特征不稳定。
- 如果独立测试集召回很低，说明大量延误订单被漏掉，需要调整阈值或换算法。
- 如果不同年份数据差异很大，按时间切分的评估结果更可信。

## 第九步：把结果整理进论文

### 9.1 建议的报告结构

1. 数据来源与字段说明。
2. 数据清洗流程：关联、去重、缺失值、异常值、时间逻辑。
3. 延误标签定义：
   `is_delayed = order_delivered_customer_date > order_estimated_delivery_date`。
4. 描述性统计：
   - 订单量、已签收量、延误量、延误率。
   - 平均配送时长、平均延误天数。
   - 按月、星期、类目、州的延误率。
   - 配送距离与配送时长/评分的关系。
5. 特征工程与特征选择。
6. 模型与超参数、数据划分、交叉验证。
7. 评估结果：AUC、召回、精确率、F1、混淆矩阵、ROC/PR。
8. 可解释性：全局特征重要性、单样本 SHAP、反事实。
9. 结论与业务建议。

### 9.2 一张可直接用的结果表

| 模型 | ROC-AUC | 宏 F1 | 正类召回 | 正类精确率 | 训练耗时 |

| 逻辑回归 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 |
| 随机森林 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 |
| XGBoost | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 |
| LightGBM | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 | 以页面为准 |

不要只写准确率。延误样本只占约 8%，全部预测“未延误”也能得到 92% 的准确率，但没有业务价值。

### 9.3 可解释性怎么写

- 全局：SHAP 重要性前 5 的特征，例如距离、运费占比、客户州、下单月份、商品类目。
- 单样本：挑一条“预测延误”的订单，写清楚哪些特征推高、哪些拉低。

## 11. 常见问题

### 11.1 页面提示“工作流尚未保存”

系统现在会自动保存工作流，训练前也会强制保存一次。如果仍然出现：

1. 点顶部保存图标（✓）。
2. 看顶部状态是否从“未保存”变成“已自动保存”。
3. 检查网络和登录是否过期。
4. 刷新页面后重试。

### 11.2 新建工作流报 500

该问题已修复，正常会返回 201。如果再次出现，检查模型管理服务（8085）日志和数据库连接。

### 11.3 提示“训练数据需要 12 到 100,000 行”

当前表行数不满足限制。处理办法：

1. 在数据处理模块用“行筛选”缩小时间范围。
2. 用“分组聚合”把明细聚合到订单级。
3. 换一个更小的数据版本。
4. 使用 `orders_delay_train70.csv`（67,529 行）。

### 11.4 提示“目标列只有一个值”

目标变量在当前数据里只有一种取值，无法训练分类模型。检查：

1. 是否误选了 `is_delayed` 之外的字段。
2. 数据过滤后是否只剩延误订单或只剩未延误订单。
3. 是否把目标字段选成了常量。

### 11.5 训练失败或超时

1. 减少特征数量。
2. 减少行数或改用 3 折交叉验证。
3. 换更轻量的算法：逻辑回归、决策树、LightGBM。
4. 关闭其他占用内存的程序。
5. 分批训练不同算法。

### 11.6 SVM / KNN 结果和全量数据不一致

这两个算法在数据量大时会自动抽样（SVM 约 2 万行，KNN 约 3 万行），算法卡片上有说明。论文里要写明实际参与训练的行数。

### 11.7 分析页没有图

1. 确认已经选择数据集、版本和数据表。
2. 确认点击了字段名，而不是只勾选复选框。
3. 类别字段显示频数，数值字段显示直方图。
4. 两个类别字段不支持关系分析，换一个数值字段作为 Y。

### 11.8 PDF 中文乱码

报告 PDF 已使用中文字体。如果仍然乱码：

1. 重新生成一次。
2. 改用 Word 或 HTML 格式。
3. 检查报告标题是否包含特殊字符。

### 11.9 登录后接口 401

Keycloak 令牌约 5 分钟过期。刷新页面重新登录即可。批量操作时尽量在登录后连续完成。
